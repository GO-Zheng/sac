一、 用例编号（如 TC-INV-01、TC-CHAOS-01）的由来与设计哲学

这个编号体系来源于国际软件工程测试标准（IEEE 829 / ISO/IEC/IEEE 29119）与可靠性工程实践，并结合了 SAC 的可寻址需求。它由三部分构成：

text
    TC    -    INV    -    01
   [前缀]     [类别/维度]   [序号]
1. TC —— 实体类型标识 (Test Case)
由来：全球软件测试领域事实上的通用前缀缩写（Test Case）。
作用：在整个 SAC 资产图谱中建立全局唯一命名空间，一眼区分不同类型的工程资产：
ADR-0001：架构决策记录 (Architecture Decision Record)
SPEC-WAL-01：物理规约条款 (Specification)
REQ-001：产品需求条款 (Requirement)
TC-xxx：测试用例与验证契约 (Test Case)
当代码抛错或 CI 报警提示“TC-INV-03 failed”时，人类或 AI 在全库搜索该字符串，能瞬间命中唯一的规约条目。
2. 中间段 —— 测试分类与验证维度 (Category Token)

在基础软件（尤其是存储引擎、数据库和分布式系统）中，测试不是扁平的，而是有完全不同的故障等级和物理关注点。使用中间段可以一眼识别其“防御重点”：

标识符	全称	关注维度与防御目标	严重等级
INV	Invariant (不变式)	系统的数学与业务定律。
验证在正常、合法操作下必须永恒成立的定理（如：覆盖写取最新值、幂等删除、写持久性）。任何破坏均为 P0 核心逻辑 Bug。	P0 (不可违背)
CHAOS	Chaos / Fault (混沌注入)	系统的物理断电与介质损坏韧性。
验证突发硬件级灾难（掉电截断 Torn Write、闪存坏道位翻转 Bit Rot）下的自愈截断与报错防守能力。	P1 (容灾韧性)
CONC	Concurrency (并发竞争)	多线程竞态与死锁防御。
高并发交叉读写、写锁竞争下的无锁点查延迟与数据可见性。	P1 (并发安全)
PERF	Performance (性能基准)	延迟与吞吐门禁。
P99 尾部延迟、点查 QPS、落盘吞吐防退化基准。	P2 (性能防护)

备选风格讨论： 除了按“测试类型（INV / CHAOS）”划分外，业界还有一种是按“子系统模块（MEM / WAL / SST）”划分，例如 TC-WAL-01、TC-MEM-01。 我们目前选择 TC-INV 与 TC-CHAOS 的原因是：同一个不变式（如写持久性）往往跨越了 WAL 和 MemTable 两个模块，按**关注维度（不变式 vs 故障注入）**划分对系统契约的抽象度更高。

3. 后缀段 —— 两位固定宽度自增序号 (01, 02...)
采用 01, 02 两位对齐格式（若用例超过百个可用三位 001）；
作用是保证在 Markdown 表格中天然垂直对齐，且排版美观、检索精准。
